## 1. ภาพรวมผลิตภัณฑ์ (สไลด์เปิด)

**YooNai (TimeLine HR)** — ระบบ HR แบบ SaaS multi-tenant สำหรับบริษัท SME ไทย ขายให้ลูกค้าหลายบริษัทผ่าน Vendor

| ส่วน | ผู้ใช้ | ช่องทาง |
|---|---|---|
| Admin (เว็บ) | HR, ผู้จัดการ, ผู้บริหาร, เจ้าของระบบ | Web App |
| Employee (มือถือ) | พนักงานทุกคน | LINE LIFF |
| Super Admin | ทีมผู้พัฒนา/ขาย (Vendor) | Web App แยก |

**ความสามารถหลัก:** เช็คอินตามกะ (GPS / QR / Geofence) · ลา และ วันหยุด · จองวันหยุดประจำสัปดาห์ · OT · คำขอลาออก · ขอเอกสาร HR · ประกาศ · รายงาน · บันทึกกิจกรรม

**หลักการออกแบบ:** ใช้ได้ทันทีโดยไม่ต้องฝึก · ข้อมูลที่ต้องการเจอใน 1–2 คลิก · ออกแบบสำหรับภาษาไทย · Workflow มาก่อนความสวย · ใช้ได้บนมือถือ

## 2. User Persona

### Persona 1 — HR Admin ("พี่นุ่น", 34, ผู้ใช้หลัก)

| หัวข้อ | รายละเอียด |
|---|---|
| บทบาท | HR/ธุรการ ดูแลพนักงาน 30–150 คน หลายสาขา |
| ใช้ระบบ | ทุกวันบนคอมพิวเตอร์ในสำนักงาน |
| เป้าหมาย | รู้ว่าวันนี้ใครมา/สาย/ลา · อนุมัติคำขอให้ทัน · ปิดรายงานสิ้นเดือนได้ไม่ต้องคีย์ซ้ำ |
| งานประจำ | ตรวจเช็คอินตอนเช้า · อนุมัติลา/OT · ลงวันหยุดให้พนักงาน · ออกเอกสารรับรอง · ส่งรายงานให้ผู้บริหาร |
| Pain point | ข้อมูลกระจาย (Excel, LINE กลุ่ม) · พนักงานลืมเช็คอินแล้วต้องลงแทน · ต้องไล่ดูว่าใครโควต้าหยุดเหลือเท่าไร · ลืมรหัสผ่านต้องรอคนช่วย |
| ความคาดหวัง | หน้าเดียวเห็นภาพรวม · สีและสถานะแยกออกทันที · ไม่ต้องมีคู่มือหนา |
| ความเสี่ยงถ้าระบบไม่ดี | กลับไปใช้ Excel · ตัวเลขขาด/สายผิด ทำให้ทะเลาะกับพนักงาน |

### Persona 2 — หัวหน้าสาขา / หัวหน้าแผนก ("พี่โอ๊ต", 41)

| หัวข้อ | รายละเอียด |

### Persona 3 — พนักงานหน้างาน ("น้องเหมียว", 26)

| หัวข้อ | รายละเอียด |
|---|---|
| บทบาท | พนักงานประจำกะ ทำงานตามสาขา |
| ใช้ระบบ | มือถือผ่าน LINE ไม่ติดตั้งแอปเพิ่ม วันละ 2 ครั้ง (เข้า/ออก) |
| เป้าหมาย | เช็คอินให้เสร็จใน 10 วินาที · ขอลา/จองวันหยุดโดยไม่ต้องทักหัวหน้า · เห็นวันหยุดและวันลาของตัวเอง |
| Pain point | GPS ไม่แม่น เช็คอินไม่ผ่าน · ไม่แน่ใจว่าโดนหักเพราะสายหรือไม่ · ไม่รู้ว่าเหลือวันหยุดกี่วัน · หน้าจอค้างเลื่อนไม่ได้หลังเช็คอิน (เคยเกิด แก้แล้ว) |

### Persona 4 — ผู้บริหาร ("คุณบอส", 52, อ่านอย่างเดียว)

| Pain point | ถูกนับเป็น "ยังไม่เช็ค/ขาด" ทั้งที่ไม่ต้องเช็คอิน (แก้แล้ว: ตั้งค่า "ไม่ต้องเช็คอิน") |

### Persona 5 — เจ้าของระบบฝั่งบริษัทลูกค้า (Root Admin, "คุณแพร", 45)

| หัวข้อ | รายละเอียด |
|---|---|

| เป้าหมาย | คุมว่าใครเข้าถึงข้อมูลอะไร · มอบสิทธิ์ให้ผู้ใช้อื่นเอง |

| Pain point | ผู้ใช้ลืมรหัสผ่านแล้วต้องมาขอรีเซ็ต · อยากรู้ว่าใครแก้อะไร |

### Persona 6 — ทีม Vendor / Super Admin (ผู้พัฒนาและขาย)

| หัวข้อ | รายละเอียด |
|---|---|
| เป้าหมาย | เปิดบริษัทใหม่ได้เร็ว (สร้าง tenant, ตั้ง LINE OA) · ย้ายข้อมูลจากระบบเดิม · ดูแลหลายลูกค้าโดยไม่พัง |

## 3. Journey Map

### 3.1 Journey ของ HR Admin — วงจรหนึ่งเดือน

| ช่วง | สิ่งที่ทำ | จุดสัมผัส | ความรู้สึก | Pain point | โอกาส / ที่ระบบทำแล้ว |
|---|---|---|---|---|---|
| 1. เริ่มใช้งาน | รับบัญชี ตั้งรหัสผ่าน สร้างสาขา กะ พนักงาน | หน้า Login, คู่มือ /manual | กังวล | ไม่รู้เริ่มตรงไหน | คู่มือในระบบพร้อมภาพจริง · ตั้งพิกัดสาขา+รัศมี |
| 2. เช้าทุกวัน | ดูแดชบอร์ด ใครมา/สาย/ยังไม่เช็ค | Dashboard, หน้าเช็คอิน | ตื่นตัว | ปนกันระหว่าง "ลา/หยุด" กับ "ยังไม่เช็ค" | แยกสี หยุด/ลา ขึ้นก่อน · การ์ดสรุปกดดูรายชื่อได้ |
| 3. ระหว่างวัน | พนักงานลืมเช็คอิน ลงบันทึกแทน | หน้าเช็คอิน → "+ ลงบันทึก" | หงุดหงิด | ต้องกรอกเวลา/กะเอง | ลงแทนได้ · สายตามเวลาจริง |
| 4. อนุมัติ | อนุมัติลา OT ลาออก ขอเอกสาร | เมนูตามงาน + ตัวเลขแจ้งเตือนบนเมนู | โล่งเมื่อเคลียร์หมด | งานรออนุมัติกระจายหลายหน้า | ป้ายตัวเลขบนเมนู + กระดิ่ง |
| 5. วางแผนวันหยุด | ดูปฏิทินรวม ลงวันหยุดรายคน/หลายคน | การลา และ วันหยุด → ปฏิทินรวม | ปวดหัวช่วงสิ้นเดือน | ใครหยุดวันไหนดูยาก · โควต้าไม่ชัด | มุมมองรายคน · ลงหลายคนพร้อมกัน · การ์ดสรุปรายเดือน |
| 6. สิ้นเดือน | ดึงรายงาน ส่งผู้บริหาร ออกเอกสาร | รายงาน, Excel/PDF, ขอเอกสาร HR | เหนื่อยแต่เร่ง | คีย์ซ้ำ ข้อมูลไม่ตรงกัน | รายงานหลายมุม · เอกสารรับรองสร้างในระบบ |
| 7. เมื่อมีปัญหา | ลืมรหัสผ่าน / แก้ข้อมูลผิด | หน้าลืมรหัสผ่าน, บันทึกกิจกรรม | ตื่นตระหนก | ต้องรอคนรีเซ็ต | OTP ทางอีเมล · audit log ตรวจย้อนหลัง |

**อารมณ์โดยรวม:** เริ่มกังวล → มั่นใจเมื่อเห็นภาพรวมตอนเช้า → เครียดช่วงปิดเดือน → ลดลงเมื่อรายงานออกเอง

### 3.2 Journey ของพนักงาน — หนึ่งวันทำงาน

| ช่วง | สิ่งที่ทำ | จุดสัมผัส | ความรู้สึก | Pain point | ที่ระบบทำแล้ว |
|---|---|---|---|---|---|
| 1. เริ่มใช้ครั้งแรก | กดลิงก์จาก LINE ผูกบัญชีกับชื่อตัวเอง | LINE OA, LIFF | ลังเล | กลัวผูกผิดคน | เลือกชื่อจากรายการ + ยืนยัน |
| 2. ก่อนเข้างาน | เปิดแอปผ่าน LINE เช็คอิน | หน้าเช็คอิน (มาสคอตนกฮูก) | เร่งรีบ | GPS ไม่แม่น เช็คอินไม่ผ่าน | โหมดแจ้งเตือน (WARN) / บล็อก (BLOCK) · ต้องมี GPS ในโหมดบล็อก · สแกน QR ได้ |
| 3. ผลลัพธ์ | เห็นสถานะ ตรงเวลา/สาย | ป๊อปอัปผลลัพธ์ | โล่ง หรือ เสียใจ | ไม่รู้ว่าโดนหักเท่าไร | แสดงระดับสาย ค่าปรับ ชัดเจน |
| 4. ระหว่างเดือน | จองวันหยุดประจำสัปดาห์ ขอลา | เมนูวันลา / หยุด | คาดหวัง | ไม่รู้โควต้าเหลือ ไม่รู้วันไหนจองได้ | ปฏิทิน "วันหยุดของฉัน" รวมหยุด ลา นักขัตฤกษ์ ตามสิทธิ |
| 5. รออนุมัติ | รอผลจากหัวหน้า | แจ้งเตือน LINE | กังวล | ไม่รู้ว่าถึงไหนแล้ว | สถานะรออนุมัติ/อนุมัติ/ปฏิเสธ + แจ้งผลทาง LINE |
| 6. ตรวจสอบ | ดูประวัติเช็คอิน | หน้าประวัติ | สบายใจ/สงสัย | ข้อมูลผิดแก้ไม่ได้เอง | ดูประวัติรายเดือน · แจ้ง HR แก้ |
| 7. ต้องการเอกสาร | ขอใบรับรองเงินเดือน / รับรองการทำงาน | ขอเอกสาร | ใจร้อน | ต้องรอ HR พิมพ์ | ยื่นคำขอในระบบ HR สร้างเอกสารให้ |

## 4. ขอบเขตงาน (Scope)

### ขอบเขตที่ทำแล้ว (In Scope)
- **Admin เว็บ:** แดชบอร์ด · สาขา/กะ · พนักงาน (ข้อมูลส่วนตัว นโยบาย สถานะ) · Master Data · เช็คอิน · การลา และ วันหยุด · เช็คอินนอกสถานที่ · OT · คำขอลาออก · ขอเอกสาร HR · ประกาศ · รายงาน 7 หมวด · บันทึกกิจกรรม · ตั้งค่า · คู่มือในระบบ
- **Employee (LINE LIFF):** เช็คอิน · ประวัติ · ลา/วันหยุด · โปรไฟล์ · คู่มือสไลด์
- **ความปลอดภัย:** แยก tenant · สิทธิ์ละเอียดต่อเมนู · OTP ลืมรหัสผ่านทางอีเมล · เฉพาะ Root Admin มอบสิทธิ์
- **Infrastructure:** Fastify + Prisma + MariaDB บน VPS (Docker) · Vercel 3 โปรเจกต์ (admin / employee / superadmin)

### อยู่นอกขอบเขต / ยังไม่ทำ
- ระบบคำนวณเงินเดือนเต็มรูปแบบ
- แอปมือถือ native (ใช้ LINE LIFF แทน)
- KPI / คะแนนวินัยรวม (ได้วิเคราะห์ข้อมูลที่มีแล้ว ยังไม่สร้างหน้า)

### งานค้าง / ข้อเสนอถัดไป
- เตือนสาขาที่ยังไม่ปักพิกัด และแสดงสถานะ "ไม่ได้ตรวจรัศมี"
- เก็บค่าความแม่นยำ GPS (accuracy) เพื่อแยกตำแหน่งจริงกับตำแหน่งประมาณ
- จำกัดอัตราการขอ OTP ตาม IP · OTP สำหรับ Super Admin
- ให้แดชบอร์ดนับวันหยุดเสาร์-อาทิตย์/นักขัตฤกษ์ในรายการ "ไม่ต้องเช็ค"
- ตั้งอีเมลกู้รหัสผ่านให้ 8 บัญชีที่ยังไม่มี

```
→ 7 ผู้ใช้รีวิว/อนุมัติ → 8 ปล่อยใช้งาน (Deploy) → 9 อัปเดตคู่มือ & เก็บ Feedback → (วนกลับข้อ 1)
```

### รายละเอียดแต่ละขั้น

| # | ขั้นตอน | สิ่งที่ทำ | ผลลัพธ์ที่ได้ |
|---|---|---|---|
| 1 | **เก็บ Requirement** | รับคำขอจากผู้ใช้/ลูกค้า (ข้อความ ภาพหน้าจอ ตัวอย่างอ้างอิง) · สังเกตปัญหาจากการใช้งานจริง | รายการคำขอพร้อมภาพประกอบ |
| 2 | **วิเคราะห์ & กำหนดขอบเขต** | ตรวจโค้ด/ข้อมูลจริงว่าปัญหาคืออะไร (เช่น สาขาไม่มีพิกัดจึงไม่ตรวจรัศมี) · แยกว่าเป็นบั๊ก ฟีเจอร์ใหม่ หรือเรื่องข้อมูล · ถามเฉพาะเมื่อการตัดสินใจเป็นของเจ้าของงานจริงๆ | ขอบเขตงานที่ชัด + ข้อเสนอ |
| 3 | **จัดลำดับความสำคัญ** | บั๊กที่กระทบการใช้งานจริงมาก่อน (เช่น เลื่อนหน้าจอไม่ได้หลังเช็คอิน) → ฟีเจอร์ → ปรับดีไซน์ | คิวงาน |
| 4 | **ออกแบบ** | ใช้ภาพอ้างอิงจากผู้ใช้ · รักษา tone เดียวกันทั้งฝั่ง admin และพนักงาน · วางโครงข้อมูล/Migration ถ้าต้องเพิ่มตาราง | แบบ UI + schema |
| 5 | **พัฒนา** | แก้ทีละส่วน ตามแบบแผนโค้ดเดิม · เขียน Migration ด้วยมือ · เก็บความเข้ากันได้ย้อนหลัง | โค้ดที่เปลี่ยน |
| 6 | **ตรวจสอบ** | `tsc --noEmit` (admin, employee, server) · `vitest` ฝั่ง server · ถ่ายภาพหน้าจอจำลองข้อมูลจริงด้วย Puppeteer เพื่อตรวจหน้าตา · ตรวจ error ในคอนโซล | ผ่าน typecheck/test + ภาพตรวจ |
| 7 | **ผู้ใช้รีวิว/อนุมัติ** | รายงานผลเป็นภาษาไทยสั้นๆ พร้อมระบุสิ่งที่ยังไม่ได้ตรวจ · **ไม่ push ก่อนผู้ใช้สั่ง** | คำสั่ง "push" จากเจ้าของงาน |
| 8 | **ปล่อยใช้งาน** | commit + push → Vercel build อัตโนมัติ 3 โปรเจกต์ · ถ้าแก้เซิร์ฟเวอร์: SSH → `git pull` → build Docker → `prisma migrate deploy` → `up -d` · ตรวจสถานะ Vercel ผ่าน GitHub status | ระบบ production เวอร์ชันใหม่ |
| 9 | **อัปเดตคู่มือ & Feedback** | แก้หน้าจอ admin ทุกครั้ง → ต้องอัปเดตคู่มือในระบบ (ข้อความ + ภาพถ่ายใหม่) ในคอมมิตเดียวกัน · บันทึกสิ่งที่เรียนรู้ลง brain/ และ memory · รับ feedback รอบใหม่ | คู่มือตรงกับระบบ + ความรู้สะสม |

### กฎการทำงานที่ยึดถือ
1. **ไม่ push / deploy ก่อนได้รับอนุญาต** และไม่แตะ production config หรือ secret โดยไม่ถาม
2. **ตรวจข้อมูลจริงแบบอ่านอย่างเดียว** ก่อนสรุปสาเหตุ (ไม่แก้ข้อมูล production เอง)
3. **รายงานตามจริง** — ถ้ายังไม่ได้ตรวจส่วนไหน ต้องบอก
4. **ภาพคู่มือต้องไม่มีข้อมูลจริง** — ถ่ายจากข้อมูลจำลอง
5. **แยกสิทธิ์ชัด** — Manager = Admin ในการเข้าถึงข้อมูล ยกเว้นการมอบสิทธิ์ให้ผู้อื่น

### ตัวอย่างวงจรจริง (Case Study สำหรับสไลด์)
**เรื่อง: "เหมียวอยู่ในรัศมีด้วยหรือ?"**
1. Requirement — ผู้ใช้ส่งภาพแผนที่ถามว่าพนักงานอยู่ในรัศมีเช็คอินหรือไม่
2. วิเคราะห์ — ตรวจข้อมูลจริง พบว่าสาขาไม่มีพิกัด ระบบจึงข้ามการตรวจรัศมี และพิกัดของพนักงานมีลักษณะเป็นเลขกลมผิดปกติ
3. ตัดสินใจ — ให้ผู้ใช้ปักพิกัดสาขาเอง (ข้อมูลของเขา) · เสนอเพิ่มการเตือนในระบบ
4. ผลลัพธ์ — ผู้ใช้เข้าใจว่ารัศมี 2 ที่ (สาขา/กะ) ทำงานอย่างไร และต้องปักพิกัดก่อน
