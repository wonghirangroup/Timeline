## หน้า 2 — ระบบนี้คืออะไร
**หัวข้อ:** 1 ระบบ 3 ฝั่งผู้ใช้
**เนื้อหาบนสไลด์:**
- **Admin (เว็บ)** — HR, ผู้จัดการ, ผู้บริหาร, เจ้าของระบบ
- **พนักงาน (LINE)** — เช็คอิน ลา จองวันหยุด ไม่ต้องติดตั้งแอป
- **Vendor (Super Admin)** — เปิดบริษัทลูกค้า ตั้งค่า LINE OA
- ความสามารถหลัก: เช็คอินตามกะ (GPS/QR) · ลาและวันหยุด · OT · ลาออก · ขอเอกสาร HR · รายงาน
**ภาพ/ผัง:** 3 กล่องเรียงกัน พร้อมไอคอน (คอมพิวเตอร์ / มือถือ-LINE / เซิร์ฟเวอร์) ลูกศรเชื่อมไปที่ฐานข้อมูลกลาง
**หมายเหตุผู้พูด:** เป็นระบบ multi-tenant ขายให้หลายบริษัท แต่ละบริษัทข้อมูลแยกกัน
**ภาพประกอบ:** `01-overview__dashboard.png`, `01-overview__navigation.png`

## หน้า 3 — ผู้ใช้ทั้ง 6 กลุ่ม
**หัวข้อ:** เราออกแบบให้ใคร
**เนื้อหาบนสไลด์ (การ์ดคน 6 ใบ ชื่อสมมติ):**
1. **พี่นุ่น** — HR Admin ผู้ใช้หลัก ดูแลพนักงาน 30–150 คน
2. **พี่โอ๊ต** — หัวหน้าสาขา/แผนก ใช้มือถือ อนุมัติระหว่างเดินงาน
3. **น้องเหมียว** — พนักงานหน้างาน เช็คอินวันละ 2 ครั้งผ่าน LINE
4. **คุณบอส** — ผู้บริหาร ดูสรุปอย่างเดียว ไม่เช็คอินเอง
5. **คุณแพร** — เจ้าของระบบฝั่งบริษัท มอบสิทธิ์ให้คนอื่นได้
6. **ทีม Vendor** — เปิดบริษัทใหม่ ย้ายข้อมูลจากระบบเก่า
**ภาพ/ผัง:** การ์ดคน 6 ใบ (2 แถว × 3) ใบละ 1 ไอคอนบทบาท
**หมายเหตุผู้พูด:** เป็น proto-persona สร้างจากบทบาทในระบบและปัญหาที่เกิดจริง ชื่อสมมติ

## หน้า 4 — Persona: HR Admin
**หัวข้อ:** พี่นุ่น — HR Admin (34)
**เนื้อหาบนสไลด์:**
- **เป้าหมาย:** รู้ว่าวันนี้ใครมา/สาย/ลา · อนุมัติทัน · ปิดรายงานสิ้นเดือนไม่ต้องคีย์ซ้ำ
- **Pain point:** ข้อมูลกระจาย Excel/LINE กลุ่ม · ต้องลงบันทึกแทนคนลืมเช็คอิน · ไล่ดูโควต้าหยุดทีละคน · ลืมรหัสผ่านต้องรอคนช่วย
- **ความคาดหวัง:** หน้าเดียวเห็นภาพรวม · สีสถานะแยกออกทันที · ไม่ต้องอ่านคู่มือหนา
- **ถ้าระบบไม่ดี:** กลับไปใช้ Excel
**ภาพ/ผัง:** รูปการ์ดคนกลางหน้า ซ้ายเป็นเป้าหมาย ขวาเป็น pain point
**ภาพประกอบ:** `01-overview__dashboard.png`

## หน้า 6 — Persona: หัวหน้า ผู้บริหาร เจ้าของระบบ
**หัวข้อ:** อีก 3 บทบาทที่ต้องดูแล
**เนื้อหาบนสไลด์ (3 คอลัมน์):**

## หน้า 7 — Journey: HR Admin
**หัวข้อ:** วงจรหนึ่งเดือนของ HR Admin
**เนื้อหาบนสไลด์ (เส้นเวลา 7 ช่วง + อารมณ์):**
1. **เริ่มใช้งาน** (กังวล) — ตั้งสาขา กะ พนักงาน
2. **เช้าทุกวัน** (ตื่นตัว) — ดูแดชบอร์ด ใครมา/สาย/ยังไม่เช็ค
3. **ระหว่างวัน** (หงุดหงิด) — ลงบันทึกแทนคนลืมเช็คอิน
4. **อนุมัติ** (โล่ง) — ลา OT ลาออก ขอเอกสาร
5. **วางแผนวันหยุด** (ปวดหัว) — ปฏิทินรวม ลงวันหยุดหลายคน
6. **สิ้นเดือน** (เหนื่อยแต่เร่ง) — รายงานและเอกสาร
7. **เมื่อมีปัญหา** (ตื่นตระหนก) — ลืมรหัสผ่าน แก้ข้อมูลผิด
**ภาพ/ผัง:** เส้นเวลาแนวนอน มีเส้นกราฟอารมณ์ขึ้น-ลงทับ ไอคอนหน้ายิ้ม/เครียดตามช่วง
**ภาพประกอบ:** `02-hr-daily__attendance-today.png`

## หน้า 8 — Journey: HR Admin (ระบบแก้อะไรให้)
**หัวข้อ:** จุดเจ็บ → สิ่งที่ระบบทำให้
**เนื้อหาบนสไลด์ (ตาราง 2 คอลัมน์ ซ้าย = ปัญหา / ขวา = ที่ทำแล้ว):**
- ปน "ลา/หยุด" กับ "ยังไม่เช็ค" → แยกสี ม่วง/เทา และเรียงหยุด/ลาขึ้นก่อน
- งานรออนุมัติกระจายหลายหน้า → ป้ายตัวเลขบนเมนู + กระดิ่ง
- ใครหยุดวันไหนดูยาก → ปฏิทินรวม + มุมมองรายคน + ลงหลายคนพร้อมกัน
- คีย์รายงานซ้ำ → รายงาน 7 หมวด ส่งออก Excel/PDF
- ลืมรหัสผ่าน → OTP ทางอีเมล
**ภาพ/ผัง:** ลูกศรจากซ้ายไปขวาทุกแถว
**ภาพประกอบ:** `04-hr-dayoff__team-calendar.png`, `02-hr-daily__attendance-today.png`

## หน้า 13 — ขั้นที่ 1: เก็บ Requirement
**หัวข้อ:** ขั้น 1 — เก็บ Requirement
**เนื้อหาบนสไลด์:**
- **ใครทำ:** เจ้าของงานส่งคำขอ · ผู้พัฒนารับ
- **Input:** ข้อความสั้น · ภาพหน้าจอชี้ปัญหา · ภาพอ้างอิงดีไซน์
- **ทำอะไร:** อ่านภาพให้ครบ · แยกเป็น บั๊ก / ฟีเจอร์ใหม่ / ปรับดีไซน์ / คำถามข้อมูล
- **Output:** รายการคำขอ 1 เรื่อง ต่อ 1 รายการ พร้อมภาพ
- **Gate:** ชัดพอจะลงมือไหม — ถามกลับเฉพาะเรื่องที่เป็นการตัดสินใจของเจ้าของงานจริงๆ
- **ตัวอย่างจริง:** ภาพการ์ด "หยุด/ไม่ต้องเช็ค" + ข้อความ "เอาการ์ดนี้ออกจากแดชบอร์ด" → ลงมือได้ทันที
- **กับดัก:** คำขอสั้นอาจหลายความหมาย ต้องตรวจก่อนว่ามีอยู่แล้วหรือยัง
**ภาพ/ผัง:** แถบ Input → กิจกรรม → Output แนวนอน

## หน้า 14 — ขั้นที่ 2: วิเคราะห์ & กำหนดขอบเขต
**หัวข้อ:** ขั้น 2 — ตรวจสาเหตุด้วยข้อมูลจริง
**เนื้อหาบนสไลด์:**
- **ทำอะไร:** ค้นโค้ดที่เกี่ยวข้อง · ตรวจข้อมูลจริงบน production (อ่านอย่างเดียว) · ประเมินผลกระทบหน้าอื่น เซิร์ฟเวอร์ คู่มือ
- **Output:** สาเหตุที่ยืนยันแล้ว + ขอบเขตที่จะแก้ + สิ่งที่ไม่แก้
- **Gate:** ถ้าต้องแก้ข้อมูลหรือ config production → ต้องถามก่อนเสมอ
- **ตัวอย่างจริง 1:** "เหมียวอยู่ในรัศมีหรือไม่" → ตรวจข้อมูลจริง พบว่าสาขาไม่มีพิกัด ระบบจึงข้ามการตรวจรัศมี = เรื่องข้อมูล ไม่ใช่บั๊ก
- **ตัวอย่างจริง 2:** "ปัดซ้ายขวาเปลี่ยนหน้า" → พบว่ามีอยู่แล้วในตัว Pagination กลาง เหลือ 2 หน้าที่ถูกปิด → ขอบเขตแคบลง
- **กับดัก:** ป้ายชื่อผิดทำให้ตัวเลขดูผิด (การ์ด "หยุดประจำ" นับคนละอย่างกับป๊อปอัป)
**ภาพ/ผัง:** แว่นขยายเหนือตาราง/ฐานข้อมูล

## หน้า 15 — ขั้นที่ 3 และ 4: จัดลำดับ + ออกแบบ
**หัวข้อ:** ขั้น 3–4 — เลือกทำอะไรก่อน แล้วออกแบบ
**เนื้อหาบนสไลด์ (2 คอลัมน์):**
- **ขั้น 3 จัดลำดับ:** บั๊กที่ใช้งานไม่ได้ → ข้อมูลผิด → ฟีเจอร์ → ปรับสี/หน้าตา · เสนอทางเลือกพร้อมคำแนะนำ · งานข้างเคียงบันทึกเป็น "ข้อเสนอถัดไป" ไม่ทำเกินสั่ง · **Gate:** เจ้าของงานตอบ "ทำเลย / ยังก่อน"
- **ขั้น 4 ออกแบบ:** ถอดองค์ประกอบจากภาพอ้างอิง · tone เดียวกันทั้งฝั่ง admin และพนักงาน · ภาษาไทยก่อน ใช้ได้บนมือถือ · สถานะที่ต่างกันต้องสีไม่คล้ายกัน · ถ้าเพิ่มข้อมูล ออกแบบ Migration ที่ไม่ทำลายข้อมูลเดิม
- **ตัวอย่างจริง:** หน้าจอเลื่อนไม่ได้หลังเช็คอิน (ใช้งานไม่ได้) ทำก่อนการปรับ sidebar · ป้าย "หยุด" เปลี่ยนเป็นม่วงเพราะซ้ำสีกับ "ยังไม่เช็ค"
**ภาพประกอบ:** `01-overview__navigation.png` (sidebar ใหม่), `04-hr-dayoff__team-calendar.png`

## หน้า 16 — ขั้นที่ 5: พัฒนา
**หัวข้อ:** ขั้น 5 — พัฒนา
**เนื้อหาบนสไลด์:**
- แก้ให้น้อยที่สุดเท่าที่ตอบโจทย์ · เขียนตามสไตล์โค้ดเดิม
- Migration ฐานข้อมูลเขียนมือ ไม่ทำลายข้อมูลเดิม
- **ตรวจสิทธิ์ที่ฝั่งเซิร์ฟเวอร์** ไม่เชื่อแค่ซ่อนปุ่มหน้าจอ
- ฟีเจอร์เวลา/เงิน คิดกรณีขอบ: ข้ามคืน ครึ่งวัน วันหยุด
- **ตัวอย่างจริง (OTP ลืมรหัสผ่าน):** เก็บรหัสแบบ hash · อายุ 10 นาที · ลองผิดได้ 5 ครั้ง · ขอซ้ำทุก 60 วินาที · ตอบเหมือนกันเสมอเพื่อไม่ให้เดาได้ว่าอีเมลมีในระบบ
- **กับดัก:** ประกาศตัวแปรหลังจุดที่ใช้ทำให้หน้ารายงานพัง
**ภาพ/ผัง:** รูปโค้ดเป็นไอคอน + โล่ความปลอดภัย

## หน้า 17 — ขั้นที่ 6: ตรวจสอบ
**หัวข้อ:** ขั้น 6 — ตรวจสอบก่อนรายงาน
**เนื้อหาบนสไลด์ (เช็กลิสต์ 5 ข้อ):**
1. ตรวจชนิดข้อมูล (typecheck) ทั้ง admin / employee / server
2. รันชุดทดสอบฝั่งเซิร์ฟเวอร์
3. รันแอปด้วยข้อมูลจำลอง ถ่ายภาพหน้าจอแล้ว **ดูภาพจริง**
4. ดู error ในคอนโซลของเบราว์เซอร์
5. ตรวจโหมดย่อ/มือถือถ้าเกี่ยวข้อง
- **Gate:** ผ่านทั้งหมดจึงรายงาน · ส่วนที่ยังไม่ได้ตรวจต้องบอกตรงๆ
- **ตัวอย่างจริง:** ตอนถ่ายภาพคู่มือ เจอ error ในหน้ารายงานเช็คอินที่ typecheck ไม่เจอ → แก้ก่อน push
- **บทเรียน:** typecheck ผ่าน ≠ หน้าจอไม่พัง
**ภาพ/ผัง:** เช็กลิสต์ติ๊กถูก 5 ข้อ

## หน้า 18 — ขั้นที่ 7: ผู้ใช้รีวิว/อนุมัติ
**หัวข้อ:** ขั้น 7 — จุดคุมสำคัญที่สุด
**เนื้อหาบนสไลด์:**
- รายงานภาษาไทยสั้นๆ: ทำอะไร · ไฟล์ไหน · ตรวจอะไรแล้ว · **ยังไม่ได้ตรวจอะไร** · มีอะไรค้าง
- เจ้าของงานดูผล แล้วสั่ง "push" หรือขอแก้
- **กฎ:** ไม่ commit / push / deploy ก่อนได้คำสั่ง · คำอนุมัติงานหนึ่งไม่ครอบคลุมงานอื่น
- **ตัวอย่างจริง:** ปรับ sidebar → รายงานผล → "push เลย" → ถึงจะ commit
- **กับดัก:** ถ้า push ไปแล้วเจอบั๊ก ต้องแจ้งตรงๆ ว่า production อาจพังอยู่
**ภาพ/ผัง:** ประตู (Gate) สีส้มกลางหน้า ลูกศรผ่านไปขั้น 8 เฉพาะเมื่อมีคำสั่ง
**ภาพประกอบ:** `09-mascot__owl-ghost.png`

## หน้า 19 — ขั้นที่ 8: ปล่อยใช้งาน
**หัวข้อ:** ขั้น 8 — Deploy
**เนื้อหาบนสไลด์ (2 เส้นทาง):**
- **ฝั่งเว็บ:** commit → push → Vercel build อัตโนมัติ 3 โปรเจกต์ (admin, employee, superadmin) → ตรวจสถานะ build
- **ฝั่งเซิร์ฟเวอร์ (ถ้าแก้):** SSH → ดึงโค้ด → build Docker → รัน migration → รีสตาร์ทบริการ
- **Gate:** ห้ามแตะ production config / secret โดยไม่ถาม (ไม่แสดงค่าคีย์)
- **ตัวอย่างจริง:** OTP อีเมล: ทดสอบส่งจริงก่อน → พบภาษาไทยเพี้ยน → ส่งใหม่ด้วย UTF-8 ถึงยืนยันว่าถูก
- **กับดัก:** ข้อจำกัดความยาวคำสั่งของ Vercel · ต้องระบุ path ของ schema ตอน migrate · การ quote คำสั่งผ่าน SSH
**ภาพ/ผัง:** ทางแยก 2 เส้นทางไปรวมที่ "production"

## หน้า 21 — ตัวอย่างจริง (Case Study)
**หัวข้อ:** "เหมียวอยู่ในรัศมีหรือไม่?"
**เนื้อหาบนสไลด์ (4 ภาพต่อเนื่อง):**
1. **คำขอ** — ผู้ใช้ส่งภาพแผนที่ ถามว่าพนักงานอยู่ในรัศมีเช็คอินไหม
2. **วิเคราะห์** — ตรวจข้อมูลจริง: สาขาไม่มีพิกัด ระบบจึงข้ามการตรวจรัศมี พิกัดพนักงานเป็นเลขกลมผิดปกติ
3. **ตัดสินใจ** — ให้เจ้าของงานปักพิกัดสาขาเอง (เป็นข้อมูลของเขา) · เสนอเพิ่มการเตือนในระบบ
4. **ผลลัพธ์** — เข้าใจว่ารัศมี 2 ที่ (สาขา/กะ) ทำงานอย่างไร และต้องปักพิกัดก่อน
**บทเรียน:** ตรวจข้อมูลจริงก่อนสรุป · ไม่แก้ข้อมูล production เอง
**ภาพ/ผัง:** 4 เฟรมแบบการ์ตูนต่อเนื่อง
