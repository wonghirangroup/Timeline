# Software Requirements Specification (SRS)

## 1. บทนำ

เอกสารนี้ระบุความต้องการเชิงหน้าที่ (Functional Requirements) และไม่ใช่หน้าที่ (Non-Functional Requirements) ของระบบ TimeLine HR ตามสถานะที่พัฒนาและใช้งานจริง ดู [Introduction.md](Introduction.md) สำหรับความเป็นมาและขอบเขตโครงการ

## 2. ภาพรวมระบบ

ระบบแบ่งเป็น 3 ระดับสิทธิ์การเข้าถึงหลัก: **Super Admin** (Vendor), **Admin/Manager/Executive/Dept Head** (บริษัทลูกค้า), และ **Employee** (พนักงาน, เข้าผ่าน LINE LIFF) — ดู [Class Diagram.md](Class%20Diagram.md) หมวด RBAC

## 3. ความต้องการเชิงหน้าที่ (Functional Requirements)

### FR-1 การยืนยันตัวตนและสิทธิ์ (Authentication & Authorization)
- FR-1.1 ระบบต้องรองรับการล็อกอินด้วย username/password (Admin/Manager) และแยกต่างหากสำหรับ Super Admin
- FR-1.2 ระบบต้องออก Access Token (อายุสั้น) และ Refresh Token (ขอ token ใหม่ได้โดยไม่ต้อง login ซ้ำ)
- FR-1.3 พนักงานต้องเข้าแอปผ่าน LINE LIFF โดยผูกบัญชีด้วย `line_user_id` อัตโนมัติ ไม่ต้องตั้งรหัสผ่านเอง
- FR-1.4 ระบบต้องรองรับ "Magic Login" — ลิงก์ล็อกอินอัตโนมัติแบบใช้ได้ครั้งเดียว หมดอายุใน 2 นาที สำหรับกดจากการแจ้งเตือน LINE เข้าเว็บแอดมินโดยไม่ต้องกรอกรหัสผ่าน
- FR-1.5 ระบบต้องจำกัดสิทธิ์ตามบทบาท (RBAC): ADMIN/MANAGER เห็นข้อมูลทั้งบริษัท, DEPT_HEAD เห็นเฉพาะแผนกที่ดูแล, EXECUTIVE เห็นได้ทั้งหมดแต่แก้ไข/อนุมัติไม่ได้ (read-only)

### FR-2 การจัดการโครงสร้างองค์กร (Organization Structure)
- FR-2.1 ระบบต้องรองรับโครงสร้างลำดับชั้น: กลุ่ม (Group) → ฝ่าย (Division) → แผนก (Department) → ตำแหน่ง (Position)
- FR-2.2 ระบบต้องรองรับหลายสาขา (Branch) ต่อบริษัท แต่ละสาขากำหนดพิกัด GPS, รัศมี (geo-fence), โหมดตรวจสอบตำแหน่ง (WARN/BLOCK) ได้เอง
- FR-2.3 นโยบาย (สิทธิ์จองวันหยุด, สิทธิ์ลา, โควต้า) ต้องตั้งค่าได้แบบ cascade จากกลุ่ม→สาขา→ฝ่าย→แผนก→ตำแหน่ง→พนักงานรายคน โดยชั้นล่างสามารถ override ชั้นบนได้

### FR-3 การจัดการพนักงาน (Employee Management)
- FR-3.1 ระบบต้องบันทึกข้อมูลพนักงาน: รหัส, ชื่อ-นามสกุล, ชื่อเล่น, เบอร์โทร, วันเกิด, วันเข้างาน, สาขาหลัก/สาขาเสริม, ตำแหน่ง, สถานะพนักงาน (ประจำ/ชั่วคราว ฯลฯ)
- FR-3.2 ระบบต้องรองรับสถานะพนักงาน: ACTIVE, INACTIVE, RESIGNED, TERMINATED พร้อมประวัติการเปลี่ยนสถานะ (Employee Status Log)
- FR-3.3 ระบบต้องรองรับการอัปโหลดรูปโปรไฟล์และเอกสารประจำตัว (บัตร ปชช., วีซ่า, ใบอนุญาตทำงาน ฯลฯ) พร้อมแจ้งเตือนก่อนหมดอายุ

### FR-4 การเช็คชื่อ (Attendance / Check-in)
- FR-4.1 พนักงานต้องเช็คอิน-เช็คเอาท์ผ่าน LIFF ได้ ระบบจับคู่กะ (shift) อัตโนมัติตามเวลาเช็คอิน
- FR-4.2 ระบบต้องรองรับกะข้ามเที่ยงคืน (overnight shift) — คำนวณ "วันของบันทึก" (attendance date) และเกณฑ์สาย/ขาดให้ถูกต้องข้ามวัน
- FR-4.3 ระบบต้องตรวจสอบตำแหน่ง GPS เทียบรัศมีสาขา (geo-fencing) ตามโหมดที่สาขาตั้งไว้ (WARN = เตือนแต่เข้าได้, BLOCK = บล็อกถ้าอยู่นอกพื้นที่ ยกเว้นสแกน QR)
- FR-4.4 ระบบต้องรองรับการเช็คอินผ่าน QR Code (สแกนแล้วยืนยันตำแหน่งอัตโนมัติ) และการลงบันทึกแทนโดยแอดมิน (manual)
- FR-4.5 ระบบต้องคำนวณสถานะมาสาย (2 ระดับ) และขาดงานอัตโนมัติ พร้อมค่าปรับตามเกณฑ์ของกะ (คิดแบบขั้นบันไดหรือต่อนาทีก็ได้)
- FR-4.6 ระบบต้องรองรับการเช็คอินนอกสถานที่ (Offsite check-in) สำหรับพนักงานที่ได้รับสิทธิ์เฉพาะราย

### FR-5 การลาและวันหยุด (Leave & Weekly-off)
- FR-5.1 พนักงานต้องยื่นคำขอลาได้ (ป่วย/กิจ/พักร้อน/คลอด/ชดเชย/ประเภทกำหนดเอง) ระบุช่วงวันที่หรือช่วงเวลา (เต็มวัน/ครึ่งวัน/กำหนดเอง)
- FR-5.2 ระบบต้องตรวจสอบโควต้าคงเหลือและแจ้งเตือนหากชนกับคนตำแหน่งเดียวกันที่ลาวันเดียวกันไว้แล้ว (ไม่บล็อก แค่แจ้งเตือนให้แอดมินเลือกตอนอนุมัติ)
- FR-5.3 ระบบต้องรองรับการจองวันหยุดประจำสัปดาห์/เดือน (Weekly-off) โดยเปิด-ปิดรอบจองต่อสาขา/เดือน พร้อม deadline
- FR-5.4 ระบบต้องคำนวณสิทธิ์วันพักร้อนตามอายุงานอัตโนมัติ (ฐาน + เพิ่มทุก N ปี ตามตำแหน่ง) พร้อมให้โบนัสรายเดือนและรีเซ็ตประจำปีผ่าน cron job
- FR-5.5 ระบบต้องรองรับวันหยุดนักขัตฤกษ์ของบริษัท กำหนดได้ต่อสาขา พร้อมเลือกได้ว่าให้ชดเชยเป็นวันชดเชยหรือวันพักร้อน

### FR-6 OT (ล่วงเวลา)
- FR-6.1 พนักงานต้องยื่นขอ OT ได้ ระบุวันที่/ช่วงเวลา/เหตุผล
- FR-6.2 ระบบต้องจำกัดชั่วโมง OT สะสมต่อสัปดาห์ และแสดงระดับเตือนเมื่อใกล้ชนเพดาน

### FR-7 คำขอลาออก (Resignation)
- FR-7.1 พนักงานต้องยื่นคำขอลาออกได้ผ่าน LIFF ระบุวันทำงานสุดท้ายและเหตุผล
- FR-7.2 เมื่อแอดมินอนุมัติ ระบบต้องเปลี่ยนสถานะพนักงานเป็น RESIGNED อัตโนมัติ และตัดสิทธิ์เข้าใช้งาน LIFF/เช็คอิน

### FR-8 เอกสาร HR
- FR-8.1 พนักงานต้องขอเอกสาร HR ได้ (สลิปเงินเดือน, หนังสือรับรองเงินเดือน, หนังสือรับรองการทำงาน)
- FR-8.2 แอดมินต้องสร้างเอกสารในระบบได้ (ดึงข้อมูลพนักงาน+บริษัทอัตโนมัติ, กรอกจำนวนเงินเอง) พร้อมเลขที่เอกสารและเก็บประวัติย้อนหลัง หรืออัปโหลดไฟล์แนบแทนก็ได้

### FR-9 ประกาศบริษัท (Announcement)
- FR-9.1 แอดมินต้อง broadcast ประกาศได้ทั้งบริษัท/เฉพาะสาขา/เฉพาะพนักงานที่เลือก พร้อมเลือกส่งแจ้งเตือนทาง LINE ได้

### FR-10 การแจ้งเตือนผ่าน LINE
- FR-10.1 ระบบต้องส่งแจ้งเตือน Flex Message ไปยังแอดมิน/หัวหน้าแผนกเมื่อมีคำขอใหม่ที่ต้องดำเนินการ พร้อมปุ่มลิงก์เข้าหน้าอนุมัติแบบ auto-login
- FR-10.2 ระบบต้องบันทึก log ทุกครั้งที่ส่งข้อความ LINE (ประเภท, ผู้รับ, สำเร็จ/ล้มเหลว) เพื่อใช้ตรวจสอบย้อนหลัง

### FR-11 รายงาน (Reports)
- FR-11.1 ระบบต้องมีรายงาน 7 หมวด: ผู้บริหาร (ภาพรวม+งานค้างอนุมัติ), พนักงาน (สรุปรายบุคคล), การเช็คอิน (ประวัติละเอียดรายวัน), สาขา (สรุปรายสาขา), วันหยุด, วันลา, การส่งข้อความไลน์
- FR-11.2 รายงานทุกหมวดต้องกรองตามเดือน/ช่วงวันที่ และสลับมุมมองการ์ด/ตารางได้

### FR-12 ระบบ Super Admin / Multi-tenant
- FR-12.1 Super Admin ต้องสร้าง/แก้ไข/ปิดใช้งาน tenant ได้ กำหนดแพ็กเกจ (FREE/STARTER/PRO/ENTERPRISE) และเพดานจำนวนพนักงาน/สาขา/กลุ่ม
- FR-12.2 Super Admin ต้องเปิด/ปิดฟีเจอร์ (feature flag) ต่อ tenant ได้ และติดตามใบแจ้งหนี้ (Invoice)

## 4. ความต้องการที่ไม่ใช่หน้าที่ (Non-Functional Requirements)

| หมวด | ความต้องการ |
|---|---|
| **Multi-tenancy** | ทุกตารางข้อมูลหลักต้องแยกด้วย `tenant_id` — ข้อมูลบริษัทหนึ่งต้องไม่รั่วไหลไปยังอีกบริษัทหนึ่งเด็ดขาด |
| **Security** | รหัสผ่านต้อง hash ด้วย bcrypt, การเข้าถึง API ต้องผ่าน JWT + ตรวจสอบ role ทุก endpoint, Magic Login token ใช้ได้ครั้งเดียวและหมดอายุเร็ว (2 นาที) |
| **Availability** | ระบบส่งแจ้งเตือน LINE ต้องเป็น best-effort — ความล้มเหลวของการแจ้งเตือนต้องไม่ทำให้ flow หลัก (สร้างคำขอ/เช็คอิน) ล้มเหลวตาม |
| **Usability** | รองรับ responsive design ทั้งจอมือถือและเดสก์ท็อปสำหรับเว็บแอดมิน, ภาษาไทยเป็นภาษาหลักของ UI |
| **Performance** | หน้ารายการ/รายงานต้องกรองข้อมูลด้วย index ที่เหมาะสม (เช่น `tenant_id + created_at`) |
| **Scalability** | สถาปัตยกรรม stateless API รองรับ horizontal scale ของ backend ได้ |
| **Maintainability** | ใช้ TypeScript ทั้ง backend/frontend, Prisma migration ทุกการเปลี่ยนแปลง schema ต้องมีไฟล์ migration บันทึกไว้ |
| **Auditability** | การกระทำสำคัญ (สร้าง/แก้ไข tenant, ล็อกอิน Super Admin, ส่งข้อความ LINE) ต้องบันทึก log ย้อนหลังได้ |

## 5. ข้อจำกัดของระบบ (Constraints)

- ต้องมีการตั้งค่า LINE Official Account + Channel Access Token ต่อ tenant ก่อนใช้ฟีเจอร์แจ้งเตือน/LIFF ได้
- การเช็คอินผ่าน QR ใช้กฎ BLOCK เสมอ (เข้มงวดกว่าค่า geo_mode ของสาขา) โดยการออกแบบ
- ระบบไม่มี payment gateway อัตโนมัติ — การเก็บเงิน/ออกใบแจ้งหนี้เป็นการบันทึกด้วยมือของ Super Admin
